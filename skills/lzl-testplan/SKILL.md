# 目标与交付边界

把“我改了这个公司项目，怎么尽可能真实地测，才能有依据交给别人或用于实际使用”转成**可执行、能判断结果的测试方案**。以当前需求、变更及实际／已约定使用为标准，不降低为演示级验收，也不承诺零风险。

默认使用者是负责本次改动的普通开发者。借鉴 `lzl-advisor` 的目标、成本和职责判断，但本技能自包含，不要求安装或调用它。不要把任务变成权限审计、全公司质量治理或完整测试执行；用户要求执行时，另行承接执行任务，沿用已确认范围但核对相应动作授权。

## 1. 先弄清什么需要被证明

优先读取当前需求、工作区变更和比较基线、相关代码／配置、现有测试及与改动有关的历史。核实基线，覆盖已提交和未提交的本次内容，避免把分支无关历史算进来。追到真实受影响入口、消费者和副作用：不能仅按修改文件名列测试，也无需遍历整个仓库。

形成简短证据链：**变更 → 受影响行为／契约 → 现实触发条件 → 应证明的结果 → 最合适的验证层**。标明来源位置或用户确认；区分事实、推断、待确认，不编造项目路径、命令、测试结果、业务指标或权限。

- 复用已确认的项目阶段、实际／约定使用、验收口径、环境、职责和授权；变化时只更新相关部分。
- 技术事实自己查。会实质改变范围或方案的业务、环境影响或授权缺口，尽早集中用普通语言询问，例如“这里连的是共用业务库还是可清理的项目测试库？”不要让新手先填写技术权限清单。
- 缺失信息只阻塞依赖它的步骤；先完成其余方案。未答复不是默认同意。明确假设和验证办法，不用一串理论风险替代有用计划。
- 身份不等于权限：普通开发者可做已授权工作；负责人头衔也不代表生产权限。能够连接或持有凭据不等于允许操作，上一阶段授权也不自动覆盖下一阶段。

## 2. 选择足够真实、成本相称的覆盖

以业务完成条件决定测试，不设固定条数、全局查询上限或人人必填的大矩阵。依据传播路径选取：正常流程、真正受影响的接口／消费者、邻近回归、实际可能触发且后果重要的失败与边界。并发、性能、安全、兼容、迁移等只在改动、契约或使用证据支持时展开；不能因复杂而漏掉必要验证，也不能把所有历史问题绑给本次改动。

对重要项分别判断三个轴：

- **必要性**：本次必需、真实但非本次必需、可选；未知时说明需要哪项证据。
- **责任**：开发者能完成什么；哪些需具体维护者／团队提供验证或接受取舍。发现不等于接管，跨团队依赖也不能因“不归我”从必需项中消失。
- **时机**：提交 review 前、联调时或实际启用前等，依据本项目约定，不统一抬升为全部必须上线前完成。

优先选择风险较低且有代表性的环境和验证层，按证据需要逐步靠近实际：单元测试能证明纯逻辑；真实数据库／服务的语义、事务、约束、权限、协议或集成是关键时，mock 的通过不能替代它们。说明版本、配置、数据形态、规模、身份或外部依赖中会影响结论的差异，以及如何补足；不为无关差异制造阻塞。

线上环境、共享环境、写入都不是一票否决项。根据实际作用对象和授权安排：已授权、隔离的项目在线测试库，可合理计划创建和清理测试数据；不能仅因“在线”退回全 mock，也不能把“测试库”标签当作无外部影响的证明。涉及状态、数据、共享或外部副作用时读取 [状态与真实环境验证](references/stateful-validation.md)。

## 3. 仅在事实会改变方案时做有限探测

允许生成方案前做少量**已有授权**的限量只读查询、连通性／元数据检查等。先明确“未知什么、哪种结果会改变哪项安排”，选择范围受控的方法；已有足够证据就停止。普通、有边界的只读核查正常推进，不反复要求用户确认抽象的负载风险。

探测不是测试执行入口：不以探测名义创建／删除数据、触发业务动作、跑全套测试、做压力测试或逐项完成计划。GET 也可能有副作用，按实际行为判断；查不到必要事实时列出待验证项，不扩大扫描。具体限量、超时与停止条件按目标系统约束选取，而非套用全局数字。

探测发现目标不符、授权拒绝、意外副作用或异常负载迹象时停止相关访问并报告事实，不绕过限制。结果不明的请求先核对是否发生，再考虑重试；被拒绝后不得原样反复尝试。仅在有实质新证据且确认先前未执行时，才考虑一次符合授权的新尝试。

## 4. 写成别人能够照着执行的方案

先给结论：当前方案是否可执行、推荐从哪里开始、哪些关键证据尚缺。用适合变更大小的结构，不机械扩写。交付至少覆盖以下内容，可合并成段落或表格：

1. **目标与边界**：这次要证明什么、覆盖哪些实际影响、哪些有依据地不纳入。
2. **环境与前置条件**：目标版本／配置、代表性与差距、数据／身份、已确认授权；仅对确有缺口的步骤标出依赖。
3. **有序场景**：每项有目的、具体输入与前置状态、操作步骤、可判定的预期及证据。按低成本快速发现问题到必要集成／真实场景组织，体现前后依赖。只在已核实项目入口时给可复制命令；未知入口给定位办法和所需补充，别伪装可执行。
4. **状态安排**：有写入时交代对象、实际影响、隔离、清理与核验；无写入的场景不硬加恢复章节。
5. **协作与授权依赖**：谁执行／谁提供什么证据、在哪一步前需要；负责人未知就明确待指派，不编造姓名，不自动发消息或授权别人行动。
6. **完成与停止标准**：怎样的实际结果算满足本次测试目标；必需项失败／阻塞如何处理；残余缺口及有权接受者；遇到什么情况停止相关动作。需要后续观察时说明目的、证据和终点，不额外创建无限跟踪任务。

证据应足以复核关键判断：实际结果、环境和版本、相关断言／输出／日志或查询摘要；避免收集无关敏感数据、泄漏凭据或堆积不能支持结论的截图。性能等阈值来自约定或证据，没有口径就注明待确认，不自造 SLA。

## 5. 最后检查结论没有越级

- **方案就绪（READY）**：步骤、判断标准和依赖已清楚。若必需信息仍缺，称“草案／部分可执行”，指出补齐办法；不把未知留成空模板却宣布全部就绪。
- **执行通过（PASS）**：只能由后续实际执行证据支持。计划中的预期结果、少量探测成功、现有测试名都不是本轮通过记录。
- **可合并／可发布／可实际启用**：还受项目流程、必需联调证据及相应授权约束。测试通过提供依据，不代替这些决定。

提交前逐项自检：关键影响有验证落点吗？必要真实性被 mock 偷换了吗？普通开发者是否能理解并照做？必要跨团队工作是否留下明确证据责任？有没有把“可回滚”当作高风险操作许可，或为无关日志／序列变化要求不可能的字节级复原？是否将计划、已做探测和待执行测试分开表述？

需要把上述原则落成完整场景时，参看 [示例：库存预留改动的测试方案](references/worked-example.md)。这是虚构演示，不是当前项目事实，也不是每个改动必须照抄的覆盖清单。
