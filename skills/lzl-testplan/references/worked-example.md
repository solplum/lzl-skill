# 示例：库存预留改动的测试方案

**以下项目、接口、文件和授权均为虚构示例，不是对当前项目的核查结果。** 用它理解如何从证据形成方案；实际使用须替换为本项目已核实的事实。测试条数和数据值只服务这个案例。

## 用户请求与已知材料

> 我是这个公司项目的普通开发，改了预留库存接口，想知道怎么测才能放心提 review。项目已有真实用户。这次改动要解决同一订单重试重复扣库存的问题。

假设当前对话和仓库提供以下材料：

- 需求：相同租户、相同订单的重复预留返回原预留，不重复扣减；相同订单改数量返回冲突。订单号只在租户内唯一；库存不足仍返回既有业务错误。
- `src/reservations/service.ts` 的本次 diff 增加幂等查找与事务；`db/migrations/042_reservation_key.sql` 增加 `(tenant_id, order_id)` 唯一索引；`src/reservations/routes.ts` 保持既有接口。
- 已核实契约：`POST /reservations` 接收 `orderId, sku, quantity`，租户从认证上下文获取；首次成功 201，重复相同请求 200、返回同一 `reservationId`，内容冲突 409，缺货 409／`INSUFFICIENT_STOCK`，非法数量 400。租户不能访问另一租户的库存或预留。
- 使用 PostgreSQL 16；迁移要求写入暂停窗口。服务提交事务后没有直接发消息或扣款，但订单服务会调用此接口；现有自动化只验证单次成功。
- 用户已获准在项目隔离的在线 QA 库和两个专属 QA 租户中创建／清理测试库存与预留；该部署已确认不会触发真实订单、计费或通知。无生产数据变更授权。
- 约定本次先提交 review，实际启用前由订单服务维护团队完成真实调用方联调。暂无新增性能承诺；生产已有重复键是否影响迁移仍未知。

### agent 怎样处理这些材料

自行读 diff、接口、迁移和部署配置，而不是先问用户“有没有 SELECT、INSERT、DELETE 权限”。复用已有 QA 授权，不因用户是普通开发者禁用 QA 写入，也不要求重复证明普通只读查询不会产生理论负载。

若缺少“同订单不同数量如何处理”的业务口径，应尽早与其他关键问题集中询问；不能自己猜成成功覆盖。这里口径已明确，无须再问。

如果 QA 引擎版本未被配置证据确认，且版本会改变迁移兼容判断，可在既有只读授权内做一次有超时的版本查询；记录返回版本即可。不要顺便创建测试订单、扫描全表、实际跑并发测试。生产重复数据未知，先设计迁移预检，由具备相应授权者在适当环境执行，不在生成方案阶段自行访问生产。

## 向用户交付的合理方案

### 结论与范围

**QA 测试部分已可执行；迁移与启用前联调的依赖已列出，但整份方案仍有待确认项。当前没有执行通过结论。** 先证明幂等、库存与租户隔离，再验证迁移和订单调用兼容。

本次覆盖预留接口、真实 PostgreSQL 事务／唯一约束、受影响的库存状态与订单调用方。不开全站回归、公司级安全审计或无依据的压力测试；未改动且无调用路径关联的报表不纳入。数据库迁移影响已有数据，是本次必需，不能因为由其他人负责就省略。

### 环境与数据

- 使用已授权的 QA 服务和 PostgreSQL 16；候选代码版本、迁移版本与 QA 配置摘要随执行记录保存。先确认部署指向 QA，而非只相信环境变量名称。
- 使用专属租户 A、B，各自测试 SKU 库存 10。每次执行以唯一 `run_id` 命名订单和 SKU；各场景使用独立 SKU，避免前一个场景改变后一个场景起点。
- 在本地或 QA 克隆验证迁移，包括构造重复数据；不在共享 QA 库故意制造破坏性历史状态。克隆中的引擎版本、旧 schema 和关键约束与目标保持一致。
- QA 不能证明生产数据已满足迁移条件，也不能代替订单服务的实际调用证据；这两项分别保留，不把其他 QA 结果作废。
- 沿用项目现有 API 测试工具与日志入口；若实际仓库不存在可用命令，就先定位／补齐执行入口，不能直接照抄不存在的 `npm test` 脚本。

### 按顺序执行的场景

以下操作是**未来执行步骤**，不是本次已做记录。每项记录请求关联标识、返回摘要及本次对象的数据库断言；敏感令牌不入报告。

| 场景与目的 | 前置状态与具体输入 | 步骤 | 可判定预期与证据 |
| --- | --- | --- | --- |
| 正常预留及顺序重试：原功能与幂等 | A 的独立 SKU 库存 10；新订单 `run_id-normal`，数量 3 | 以 A 身份 POST；保存返回 ID；再原样 POST；查该订单预留与库存 | 先 201、后 200，同一预留 ID；只一条预留，最终库存 7。保存两次响应及限定对象的查询摘要 |
| 同订单内容冲突：不能吞错或再次扣减 | 复用上一场景订单，库存 7 | 相同订单改数量为 4，再 POST | 409；原预留数量仍为 3，库存仍为 7。响应与原记录、库存前后值支持判断 |
| 并发同订单：验证真实事务／约束而非 mock | A 的新 SKU 库存 10；新订单 `run_id-race`，数量 3 | 在实际 PostgreSQL 环境同步发出两个相同请求并等候两者结束；关联两个请求的日志与记录 | 两者按契约返回首次／重复成功，无未处理 500；同一预留 ID、仅一条记录、库存 7。确认有实际重叠证据；没有重叠则该次不能证明竞争路径，调整受控测试协调方式后重测，不靠无限循环撞概率 |
| 缺货与非法数量：失败不留半成品 | 各使用新订单；对应 SKU 库存 10 | 分别提交数量 11、0、-1；每次结束核对其订单与库存 | 11 返回 409／`INSUFFICIENT_STOCK`；0、-1 返回 400；都没有新预留、库存仍为 10。沿用既有已验证输入校验覆盖，不无故扩展所有字符串排列 |
| 租户边界与键范围：变更不能串数据 | A、B 各自同名 SKU 库存 10；两个租户使用相同订单号 `run_id-tenant` | A 预留 3；B 预留 2；各自再重试；尝试以 B 身份读取 A 的预留 | A、B 获得不同预留 ID，各自重复返回自身 ID；库存分别 7、8；B 读取 A 记录按已核实访问契约拒绝且不暴露内容。保存身份别名、响应与分租户断言 |
| 迁移兼容：已有数据不能被静默破坏 | PostgreSQL 16 克隆，旧 schema；一组合法历史记录、另一组同租户同订单重复记录；包含不同租户相同订单 | 分别在干净克隆运行项目正式迁移入口；检查约束与原记录；重复数据分支记录失败行为。按照批准的部署窗口流程验证迁移与候选代码衔接 | 合法数据保留且索引生效，不同租户同订单允许存在；重复数据必须被预检／迁移明确拦截而非删除或静默合并。若迁移出现部分状态或不能安全重试，停止并交给迁移维护者制定处理方案；不能靠清空表让测试过 |

并发场景所用请求数是本案例最小竞争条件，不是通用上限。若当前实现还有不同订单竞争同一库存的改动，则补上对应超卖测试；若代码显示该路径完全复用已验证实现，可引用适用的现有测试证据并说明依据。

### 清理和核验

这些 QA 数据写入与清理均包含在已确认授权内。执行时保存本次创建对象的精确 ID，先核对 run_id、租户和状态，再按项目支持路径撤销本次预留、删除本次专属测试对象；不要按“所有 test 订单”清空数据。

清理后验证本次预留均已解除、独立 SKU 的业务状态符合清理约定、无孤立关联项，且未修改非本次对象。无需回退无业务影响的审计日志或自增序列。若发现后台任务或其他人的修改触及这些记录，暂停冲突对象的清理并协调，不覆盖最新状态。请求超时先核对请求标识／预留记录，不盲目重复创建或删除；恢复失败则停止相关后续写入、保存剩余对象清单并交给 QA 维护者。

### 必需依赖与责任止点

| 必要性／时机 | 负责方与应交付证据 | 当前状态 |
| --- | --- | --- |
| 本次必需；review 前 | 当前开发者：上述 QA 行为断言、克隆迁移结果及清理证据 | 可按计划执行，尚未执行 |
| 本次必需；实际迁移前 | 数据／迁移维护者：适当范围和负载下的既有数据预检、迁移窗口安排；若存在重复记录，提交经业务确认的数据处置方案 | 具体负责人及预检授权待确认；不把生产预检交给无相应授权的开发者 |
| 本次必需；实际启用前 | 订单服务维护团队：按真实认证／请求方式创建预留、重试及处理冲突，提交对应版本、响应和订单状态证据 | 团队已知，需按项目流程落实执行人与时间；未拿到证据不能算已联调 |

普通开发者负责自己的验证和按项目流程交接，不默认接管生产数据治理。必要跨团队证据未完成时说明对启用的影响；不是发出一条消息就算验证通过，也不额外发明流程没有要求的审批层级。

### 完成与停止标准

- QA 目标完成：适用必需场景实际通过，关键断言和运行版本可复核，清理不变量满足；未执行／失败／阻塞项分开记录。只有计划和版本探测时不能写 PASS。
- review 材料可按约定提交，但必须附迁移预检和联调的未完成依赖；是否允许合并遵循本项目流程。实际启用前补齐上述必需证据及相应授权，不能由本方案代审批。
- 发现目标连接错误、非测试记录受影响、意外外部调用、越权数据可见、库存不一致或清理失败，立即停止相关操作并保留证据；其他不依赖该问题的只读分析可继续。
- 若 QA 不具备真实并发重叠、迁移克隆不代表关键旧 schema，或调用方只做了 mock，则对应结论仍缺证据，不能以“其余都过了”替代。补足所需证据即可，不要求证明所有未知风险不存在。
